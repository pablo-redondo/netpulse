# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

NetPulse polls ~21 public internet services every few minutes (HTTP, DNS, TCP,
TLS, and a hand-rolled NTP client) and shows uptime/latency/incidents on a
dashboard. Full rationale for every non-obvious decision (why no ICMP ping,
why the topology view is illustrative, why the color palette is validated
against colorblindness, why the DB lives on Neon not Render) is in
[`README.md`](./README.md) and [`DESIGN.md`](./DESIGN.md) — both in Spanish.
Read them before making architectural changes; don't re-derive decisions
already justified there.

## Commands

Monorepo with pnpm workspaces (`apps/*`, `packages/*`). Node >=20, pnpm 10.

```bash
pnpm install

# local Postgres for apps/api (Docker required)
cd apps/api && docker compose up -d
cp apps/api/.env.example apps/api/.env
pnpm --filter @netpulse/api prisma:migrate
pnpm --filter @netpulse/api prisma:seed

# from repo root, two terminals
pnpm dev:api     # http://localhost:3001
pnpm dev:web     # http://localhost:3000

pnpm build       # pnpm -r build
pnpm lint        # pnpm -r lint
pnpm format      # prettier --write over the whole repo

pnpm test                    # runs apps/api tests only (apps/web has none)
cd apps/api && pnpm test
cd apps/api && pnpm test -- checks/strategies/http-check.strategy   # single file
cd apps/api && pnpm test:watch
cd apps/api && pnpm test:e2e
```

Set `CHECK_INTERVAL_MS=15000` in `apps/api/.env` when developing so you don't
wait 5 minutes between check rounds.

## Architecture

```
apps/api                 NestJS + Prisma + PostgreSQL (backend)
apps/web                 Next.js App Router, server components only (frontend)
packages/shared-types    CheckType / MonitoredService / CheckResult shared by both
```

**Why a monorepo**: backend and frontend pass the same data shapes back and
forth; `shared-types` keeps them from drifting silently.

### Backend (`apps/api/src`)

- `checks/strategies/*` — one strategy per check type (`http`, `dns`, `tcp`,
  `tls`, `ntp`), all implementing `CheckStrategy` (`checks.interface.ts`).
  `ChecksService` dispatches on the service's `type` field. Adding a new
  check type means adding a strategy here — it doesn't touch the scheduler.
- `schedule/schedule.service.ts` — single `@nestjs/schedule` interval
  (`CHECK_INTERVAL_MS`, default 300000ms) that loads active services, runs
  all checks in parallel via `Promise.allSettled` (so one timeout can't sink
  the others), and persists each result.
- `incidents/incidents.service.ts` — derives incidents from success/failure
  transitions in `CheckResult` (opens on first failure after a healthy run,
  closes on first success after a down run); nothing writes `Incident` rows
  directly.
- `notifications/notifications.service.ts` — posts to `ALERT_WEBHOOK_URL`
  (Discord/Slack incoming webhook) on incident open/resolve. No-op if unset.
- `history/hourly-stat.util.ts` — pure function `accumulateHourlyStat`,
  the arithmetic behind the `HourlyStat` aggregate, tested in isolation
  without a DB. The denominator for average latency is `latencyChecks`, not
  `totalChecks` — a timeout counts toward the total but has no latency to
  average in.
- `admin/seed-data.ts` — the single source of truth for the monitored-service
  catalog; both dev seed and prod `POST /admin/seed` (guarded by
  `SEED_SECRET`, header-only) read from it. It's an upsert by `name`, safe to
  re-run.
- `prisma.config.ts` routes Prisma CLI commands to `DIRECT_URL` (no pooler)
  while `PrismaService` uses `DATABASE_URL` (pooled) — migrations need
  session state that pgBouncer transaction pooling doesn't give you.

Data model: `MonitoredService` → `CheckResult` (raw, one row per check, used
for recent-checks detail) and `HourlyStat` (per-service-per-hour aggregate
that dashboard queries actually read, so a 30-day uptime query touches ~720
rows instead of ~8600). `Incident` is derived, never written directly.

### Frontend (`apps/web`)

All pages are server components that call the API directly server-side —
there is no client-side fetching and therefore no CORS to configure. API base
URL is `NETPULSE_API_URL` (`lib/api.ts`), read only on the server. The CSV
export button (`app/services/[id]/export/route.ts`) proxies the API's CSV
endpoint through a Next.js route handler since the backend URL isn't exposed
to the browser.

`apps/web/AGENTS.md` (pulled in via `apps/web/CLAUDE.md`) is regenerated by
`next dev` on every run — it's a warning that this Next.js version may differ
from training data and to check `node_modules/next/dist/docs/` before writing
Next.js-specific code. Don't hand-edit it away; committing it is expected.

## Deployment

Backend → Render (`render.yaml`, needs a persistent process for the
scheduler). Frontend → Cloudflare Workers via `@opennextjs/cloudflare`
(`apps/web/wrangler.jsonc`), because pages are server-rendered, not static.
Database → Neon, not Render (Render's free Postgres expires after 30 days and
takes the data with it — this happened once already).

Two Neon connection strings, not interchangeable: `DATABASE_URL` (pooled, for
the running app) and `DIRECT_URL` (unpooled, for `prisma migrate deploy`
only).

Cloudflare deploy commands must run with `pnpm --filter @netpulse/web ...` —
running `wrangler deploy` from the repo root fails because Wrangler won't
guess which workspace app to deploy. `wrangler.jsonc` needs
`compatibility_date` after 2025-04-01, or Wrangler-declared vars don't reach
`process.env` and the frontend falls back to `localhost` for the API URL.

## Testing conventions

Backend tests mock `fetch`, `dns.Resolver`, and `net.Socket` — no real
network calls. They're concentrated on the two places a bug wouldn't be
visually obvious: the check strategies (target parsing — `host:port`,
`hostname@resolverIP`, bare IPs — and failure modes: timeout, connection
refused, DNS failure, a real 500 vs. a network error) and the `HourlyStat`
aggregation arithmetic.
